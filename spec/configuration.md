# Configuration

Level: Core for reading the resolved configuration; Extended for resolution from layers and packages and for frozen snapshots ([README](README.md#conformance-levels)). Schema: `schemas/config.schema.json`. Test cases: `schemas/tests/config/` and `schemas/tests/resolve/` ([conformance](conformance.md#resolution)). Steps, profiles, and gates: [gates](gates.md). Plugins: [plugins](plugins.md).

## The resolved configuration

1. The protocol reads only the resolved configuration, one JSON document (`.hone/resolved.json` and the snapshots). It contains everything needed to evaluate a ticket and nothing that executes code. It is generated by `resolve` and not edited by hand.
2. Its top-level keys are `protocol` (the integer `1`), `ticket`, `kinds`, `roles`, `actors`, `steps`, `profiles`, `select`, and `plugins`, plus keys `x-<name>`. Definitions are maps whose key is the name; a definition has no inner `id`.
3. The document contains no `null`, every default is written out, and an unknown key is an error except in the namespace `x-<name>`. The content of an embedded kind schema is opaque JSON and exempt from these rules.
4. **Canonical form.** The canonical form is the RFC 8785 serialization. The hash of the document is `sha256:` followed by the lowercase hex SHA-256 of the canonical form. `resolved.json` and every snapshot contain exactly the canonical form followed by one `\n`, in UTF-8 without BOM.
5. **Self-contained.** The document has no includes and no references to other files, except plugins with a hash.
6. **Validated.** The document matches `schemas/config.schema.json`, and every reference listed in that schema's description resolves: roles, kinds, steps, profiles, gates, plugins, and statuses in gate parameters; `id_prefix` is unique across kinds; `requires` has no cycles.
7. A file recording the origin of every definition (`resolved.origin.json`) MAY exist. It is not normative and does not affect the hash.

## Roles, actors, and selection

8. A role has `kind` (`human` or `ai`) and `can`, a subset of `act`, `comment`, and `approve`. Steps and gates name only roles.
9. `actors` maps a handle to a list of roles. A person not listed in `actors` gets the roles of `"*"`; without `"*"`, such a person has no role.
10. `select` holds `rules`, a list of `{ when, profile }`, and `default`. `when` compares the ticket's `attributes`: a scalar matches by equality, a list by set membership, and every attribute of `when` MUST match. The first matching rule wins, otherwise `default`. There is no expression language.
11. A change of the attributes after the ticket started is the event `ticket.attributes_changed` ([process store](process-store.md)).

## Snapshots

12. When a ticket starts, the resolved configuration with the ticket's `overrides` is stored as a snapshot `.hone/snapshots/<hex>.json`, where `<hex>` is its hash without `sha256:`, and the ticket record names that hash in `config`. Tickets with the same configuration share one snapshot.
13. Ticket gates check a ticket against its snapshot ([gates](gates.md#what-check-runs)).
14. A deliberate switch of a ticket to a new configuration, including a change of its `overrides`, creates a new snapshot and the event `ticket.config_changed`.
15. Plugins are not frozen: a plugin file exists once, and `lock.yaml` approves exactly one hash per plugin. A ticket whose snapshot names another hash fails its plugin gates with `plugin-hash` until it switches configuration.
16. A snapshot MUST NOT be deleted while a ticket record, completed or not, refers to it.

## Layers

17. The resolved configuration is built from layers, from bottom to top: the packages (`extends`, dependencies first), the project (`.hone/`), the generators (`generate`), and the ticket's `overrides`. There is no global or personal layer. `hone/standard` is a package like any other and applies only when listed in `extends`.
18. Every package and the project's `.hone/` have this layout:

| Entry                  | Contributes to the tree                                                 |
| ---------------------- | ----------------------------------------------------------------------- |
| `kinds/<name>.yaml`    | `kinds.<name>`: the file stem is the key, the content is the definition |
| `roles/<name>.yaml`    | `roles.<name>`                                                          |
| `steps/<name>.yaml`    | `steps.<name>`                                                          |
| `profiles/<name>.yaml` | `profiles.<name>`                                                       |
| `plugins/<name>.yaml`  | `plugins.<name>`, only `capabilities` and keys `x-<name>`               |
| `select.yaml`          | the whole subtree `select`                                              |
| `actors.yaml`          | the whole subtree `actors`                                              |
| `ticket.yaml`          | the whole subtree `ticket`                                              |
| `schemas/`             | nothing: JSON files that kind schemas point to                          |
| `config.yaml`          | nothing: `extends`, and in the project also the IDs and the generators  |

19. Definition files are `.yaml` files in the strict YAML profile ([artifacts](artifacts.md#data-model-and-yaml-profile)), directly in their directory. A file whose whole content is `null` removes the definition from a lower layer. `protocol` has no file; `resolve` writes it.
20. Every other entry is an error (`layout`). In `.hone/`, `resolve` ignores `lock.yaml`, `resolved.json`, `resolved.origin.json`, `snapshots/`, and `plugins/*.wasm`. In a package, `plugins/*.wasm` is ignored, while `lock.yaml`, `resolved.json`, `resolved.origin.json`, and `snapshots/` are errors (`layout`).
21. `.hone/config.yaml` is REQUIRED. Its keys are `workspace` (`local` or a workspace ID), `project` (a project ID), `extends`, `generate`, and keys `x-<name>`. Every other key, a missing file, or a malformed value is an error (`manifest`).

## Merging

22. Objects are merged key by key, recursively. Lists are replaced.
23. `null` removes a key or a whole definition from a lower layer. An empty value is a violation of the YAML profile and removes nothing.
24. A `null` at a path that no lower layer has is an error (`null-without-target`). This includes every `null` that would otherwise remain in the result, for example inside a list or inside a definition that no lower layer has.
25. The higher layer wins. On a type conflict, the higher value replaces the lower one; the result is validated afterwards.
26. Keys `x-<name>` merge like every other key. `kinds.<type>.schema` is a leaf: a higher layer replaces or removes it, but never merges into the schema.
27. There are no explicit list operations.

## Packages

28. A package has the layout of `.hone/`. Where a package comes from is up to the tool. A package MAY have its own `config.yaml`, which contains only `extends`.
29. A reference has the form `<name>@<major>`. A name is one or more keys (lowercase with hyphens) separated by `/`.
30. **Order.** Packages are ordered depth-first, dependencies first, in the order of `extends`. In `extends: [a, b]`, `b` lies above `a`. The first occurrence of a package counts, later ones are skipped. When the project extends `[a, b]` and both extend `c`, the order is `c`, `a`, `b`, project.
31. Two majors of the same package anywhere in the tree are an error (`package-conflict`).

## Lockfile

32. `.hone/lock.yaml` has `packages`, a map from a package name to `{ version, hash }` with an exact semantic version, and `plugins`, a map from a plugin name to `{ hash, capabilities }`, the SHA-256 of the `.wasm` file and the approved capabilities. Further top-level keys are allowed only as `x-<name>`.
33. Every package, including transitive ones, has a lock entry. A reference without a lock entry, a lock entry whose major differs from the reference, and a package the tool cannot provide are errors (`package-missing`).
34. **Package hash.** The hash of a package is `sha256:` over the canonical form (RFC 8785) of a map with one entry per file of the package: the key is the path relative to the package root, with `/` as separator, in Unicode NFC; the value is `sha256:` followed by the SHA-256 of the file's bytes. A mismatch is an error (`package-hash`).
35. A malformed `lock.yaml` or package `config.yaml` is an error (`manifest`).

## Kind schemas

36. In a layer, `kinds.<type>.schema` is a string: the path of a JSON file, relative to the root of the layer that sets it. The path MUST NOT leave that layer, the file MUST exist and be JSON, and an inline schema is not allowed; each violation is an error (`schema-path`).
37. After merging, `resolve` embeds the file's content. The embedded schema is opaque: `null`, floating-point numbers, and any keys are allowed inside it, and the canonical form writes numbers as RFC 8785 prescribes.

## Plugins in the configuration

38. In a layer, `plugins/<name>.yaml` holds only `capabilities` and keys `x-<name>`. Every capability is REQUIRED except `net`, which defaults to `[]`. Any other key is an error (`shape`).
39. `resolve` adds `wasm: .hone/plugins/<name>.wasm` and `hash`, the SHA-256 of that file. If the file is missing, `lock.yaml` has no entry for the plugin, or the hashes differ, that is an error (`plugin-hash`).
40. The capabilities MUST stay within the approved ones: `read` and `net` are subsets, `timeout_ms` and `memory_pages` are at most the approved values, and `net` is `[]`. Otherwise: `plugin-capabilities`.

## Defaults

41. `resolve` writes these defaults:

| Where               | Default                                                    |
| ------------------- | ---------------------------------------------------------- |
| Role                | `kind: human`                                              |
| Profile             | `retention: archive`, `review_summary: full`               |
| Step                | `acts`, `inputs`, `outputs`, `requires`: `[]`, `gates: {}` |
| Plugin capabilities | `net: []`                                                  |
| Top level           | `kinds`, `roles`, `actors`, `steps`, `profiles`: `{}`      |

42. `plugins` is omitted when it is empty. There is no default for `select`, `ticket.path`, the `path`, `id_prefix`, and `lifecycle` of a kind, or gate `params`. Gate `params` stay as written.

## Ticket overrides

43. The field `overrides` of the ticket record is a patch on the tree with the same merge rules. It is applied after the project files and the generators and before the defaults and the hash.
44. An override MUST NOT touch `protocol`, `ticket`, `plugins`, or `kinds.<type>.schema` (`override-forbidden`). A `null` on a value that only a default would set is `null-without-target`.

## Generators

45. A generator is a plugin declared in the project's `config.yaml` under `generate`, a list of `{ plugin, hash, capabilities, into }`. It returns a patch in the shape of a layer; the patch MUST set only the part of the tree named by `into`. Only the project declares generators.
46. Generator patches are applied after the project files, in the order of `generate`, and before the ticket overrides.
47. A generator runs only on `resolve`, never on `check`.

## Resolution

48. `resolve` works in this order. It MAY stop after the first step that found errors and MAY report several errors of that step.
    1. Read `.hone/config.yaml` and `lock.yaml` (`manifest`).
    2. Order the packages, check the lock entries and the package hashes (`package-missing`, `package-conflict`, `package-hash`, `manifest`).
    3. Read every layer: layout, YAML profile, kind schema paths (`layout`, `yaml-profile`, `schema-path`).
    4. Merge the layers, then the generators, then the ticket overrides (`null-without-target`, `override-forbidden`).
    5. Embed the kind schemas and complete the plugins (`plugin-hash`, `plugin-capabilities`, `shape`).
    6. Write the defaults and `protocol: 1`.
    7. Check the shape against `schemas/config.schema.json` (`shape`), then the references (`reference`).
49. The error categories:

| Category              | Meaning                                                                     | Location |
| --------------------- | --------------------------------------------------------------------------- | -------- |
| `yaml-profile`        | A file violates the strict YAML profile                                     | file     |
| `layout`              | Unknown or forbidden entry in a layer                                       | file     |
| `manifest`            | `config.yaml` or `lock.yaml` is missing where required or malformed         | file     |
| `null-without-target` | A `null` removes nothing                                                    | pointer  |
| `package-missing`     | No matching lock entry, or the package is not available                     | file     |
| `package-hash`        | The package content does not match its pinned hash                          | file     |
| `package-conflict`    | Two majors of the same package                                              | file     |
| `schema-path`         | A kind schema path leaves its layer, does not exist, is not JSON, or inline | file     |
| `plugin-hash`         | The `.wasm` file or its lock entry is missing, or the hashes differ         | file     |
| `plugin-capabilities` | Capabilities beyond the approved ones, or `net` not empty                   | pointer  |
| `override-forbidden`  | A ticket override touches `protocol`, `ticket`, `plugins`, or a kind schema | pointer  |
| `shape`               | The result does not match `schemas/config.schema.json`                      | pointer  |
| `reference`           | A reference of the resolved document does not resolve                       | pointer  |

50. A pointer is a JSON Pointer (RFC 6901) into the resolved document; for a missing required key or an unknown key, it names that key. A file is named by its path in the layer.
