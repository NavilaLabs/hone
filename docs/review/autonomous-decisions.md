# Decisions for review

Decisions taken without the maintainer, during an autonomous run on the branch `feat/step-9-10-11`, and build-time rules that were reported but not yet confirmed. Each entry names the decision, the alternatives, and where it lives. Concept questions decided this way are marked "decided without review" in Section 15.

## Step 9: reference server (build-time rules, reported, not yet confirmed)

1. A store error on the server answers 500 with code `internal-error` and a generic message, so no server path leaks. Alternative: no body, or the real message.
2. A server answer the client cannot parse is the error `refused` with code `invalid-answer`. Alternative: `unavailable`.
3. A status without a known code is `refused` with code `http-<status>`.
4. A request without a `cursor` parameter means the empty cursor. Alternative: `invalid-request`.
5. An empty line in an append is reported as "the line is empty" (code `invalid-event`).
6. `--watch` stops pushing after the server rejected an own event, so the rejection is not repeated every 2 seconds.
7. `--watch` reconnects after 60 seconds without data on the stream.
8. A project without `actors` in the server configuration rejects every approval (fail closed).
9. A relative `data` path in `server.yaml` is resolved against the directory of the file.
10. `server.yaml` rejects unknown keys, members without an identity, two identities sharing a token, and limits that are not positive.
11. `hone serve` exits with 2 when it cannot start.
12. With both `HONE_SYNC_FOLDER` and `HONE_SYNC_SERVER` set, `hone sync` is a conflict even when only one flag is passed (clap counts environment values).
13. A server log with a hole rejects the next append to that device with `seq-gap`.
14. The server checks `Content-Length` against the limit before it reads the body.
15. An `id` the server holds at another place is `id-conflict`.
16. A subscriber also reads again at every heartbeat, so that events another process wrote into the data directory arrive.
17. An append test case without `store/` starts with an empty store (Section 14).
18. The client uses reqwest's default TLS (rustls with aws-lc-rs), which needs a C compiler to build.

## Step 9: rest

19. **Code `permission-denied`.** A file or directory of a shared folder that hone may not read, or may not write during push, is skipped and reported as `permission-denied` (Question 35), one code for reading and writing. Alternatives: `unsafe-path`, which would blur "leaves the folder"; two codes `unreadable` and `unwritable`. A permission error in the local store is skipped the same way, because the reader is shared.
20. **A denied segment ends the push.** When a segment of the own log cannot be written, push writes no later segment, as after a `fork` or an `unsafe-path`. Alternative: try the later segments, rejected because a later segment without its predecessor is a gap for every reader.
21. **A project directory that may not be examined ends the sync.** When hone may not look into the workspace directory, so that it cannot tell whether the project directory exists, sync reports `permission-denied` for the project directory and neither pulls nor pushes. Alternative: treat it as missing and try to create it, which fails the same way with a less precise report.
22. **A directory that may be listed but not entered.** When `log/` may be listed but its entries may not be examined, every device directory is reported as `permission-denied` instead of being ignored silently. A canonicalization refused for lack of permission is `permission-denied`, not `unsafe-path`.
23. **Permission tests under root.** The permission tests return early when locking a file has no effect, as for root. Alternative: fail, rejected because CI containers often run as root.

## Desktop GUI (concept Question 36)

24. **rust-ui's Dioxus components, taken as they are.** The handover assumed rust-ui supports only Leptos and asked for a port. rust-ui now publishes a Dioxus registry (MIT), so its Dioxus sources are taken and trimmed, not ported. Their Tailwind classes stay; hone's tokens stand behind rust-ui's theme names. Alternative: port the Leptos sources by hand, rejected because the result would be the same code with more room for mistakes.
25. **Theme mapping.** rust-ui's `primary` is hone's `accent` (the one primary action), rust-ui's `accent` (a hover fill) is hone's `surface-2`, `muted` and `secondary` are `surface`, `border` and `input` are `line`, `destructive` is `bad`. Every radius is 0 and every shadow is removed with one global rule, and the focus ring is an outline (2px, offset 2px). Alternative: rewrite the classes to hone's names, rejected because the handover asked to keep rust-ui's classes.
26. **A workspace of its own under `gui/`.** The web view needs WebKitGTK on Linux; in the main workspace every `cargo test` would build Dioxus and require those libraries. The precedent is `plugins/`. Alternative: `crates/hone-gui` in the main workspace.
27. **`hone log` is new.** The GUI needs the tickets and the event log, and the command line had no command that lists events. `hone log [--json]` prints `cursor` and `events` (the order of `read`). It has no filter; the GUI filters. Alternative: `hone events` without `--ticket`, rejected because its result also computes threads and steps of one ticket.
28. **Thread status is not recomputed in the GUI.** The ticket list shows the event count and the last event type from `hone log`; threads and their status come only from `hone events`, so the GUI never reimplements a protocol rule. The thread ID of an opening event (`th-` plus its UUID) is used to group a conversation, because concept Section 10 states it.
29. **Steps shown are the steps with a state.** The command line does not print a ticket's profile, so the step track shows the steps that have a `step.changed`, in the order of their first change, and setting a step takes its name as text. A `hone ticket` command that prints the profile's steps would let the track show every step; it is not added here.
30. **Gate classes in the check screen.** The ten standard gates of Section 7 are `pure`, `exec` is `exec`, every other gate is `plugin · wasm`. The command line does not print the class; adding it to `hone check --json` would remove this list from the GUI.
31. **Where `hone` is found.** `HONE_BIN`, then next to the GUI executable, then the `PATH`. The GUI passes its environment on and stores no token, no folder, and no server; writer and root are entered in the window and default to `HONE_AUTHOR`, `HONE_ROLE`, and the first argument.
32. **CSS is generated and committed.** `npm run gui:css` (Tailwind CLI 4.3.4, pinned) writes `gui/assets/hone.css`, which is committed and embedded with `include_str!`, so `cargo build` needs neither Node.js nor the Dioxus CLI. It is listed in `.prettierignore`.
33. **Fonts.** Inter and JetBrains Mono are named first and fall back to system fonts; no font files are committed and nothing is loaded from the network.
34. **Screens without a command.** Artifacts, the link graph, profiles, and plugins are left out until the command line offers them. The server screen starts `hone serve` as a child process and stops it by killing it.
35. **Windows is not tested on this machine.** The GUI uses no platform-specific code (paths through `std::path`, the executable suffix from `std::env::consts`), but it was built and run only on Linux.

## Approvals and condensation (concept Question 37)

36. **`hone approve` checks the role before writing.** The role's `can` must hold `approve`, and `actors` must give the author that role (`"*"` for persons not listed), the rule a server enforces with `role-mismatch`. Alternative: write any approval and let `approvals-valid` ignore it, rejected because the log is immutable.
37. **The last decision counts.** For every person and role, the last `approval.given` for the artifact in the order of Section 4 decides; `changes-requested` after `approved` withdraws. Alternative: any `approved` counts, rejected because a withdrawal would be impossible.
38. **`date` comes from the event ID.** The UTC date of the UUIDv7 timestamp. Alternative: the date of condensing, rejected because it would change on every run.
39. **The summary comes from a YAML file.** `--summary <file>` in the strict profile, a list of `{ q, a }` or `{ rejected }` with text values; the AI drafts the file. Under `approvals-only` a summary is refused instead of dropped silently.
40. **Condensing writes, it does not commit.** It replaces the `review` block (a top-level `review:` key and its indented lines), appends the new block at the end of the front matter or the YAML file, keeps every other byte, refuses files with carriage returns, and checks that the content hash and the parsed block are as intended. It writes a new file next to the artifact and renames it over the old one, so a link planted at the path is replaced, not written through. Strings are double-quoted and entries are flow maps in the order of the concept's example.
41. **`review.confirmed` binds the current content hash** and needs the role from `decides` of a step of the ticket's profile that outputs the artifact's kind, or, if none names `decides`, a role that may approve; `actors` must give the author that role. Alternative: bind the hash of the whole file including the block, rejected because the content hash is the one hash approvals use.
42. **No MCP tools for approvals yet.** An approval is a person's decision; an agent with a fixed author should not give one without an explicit design.
43. **Decided by the maintainer on 2026-11-19: only approvals and confirmations check `actors`.** The original finding: An automated security review suggested checking `actors` for every written event, not only approvals and confirmations. That would change the decided behaviour of `hone thread` and `hone step` (any handle with an existing role may write today, because local authorship is trust-based), so it is listed here for review instead of being changed.
44. **Not covered by tests yet:** a role without `approve`, `approvals-only`, and `decides`, because the gate test projects have none of them; covering them needs a test project with its own snapshot.
45. **Decided by the maintainer on 2026-11-19: close it with directory handles (`rustix`).** The original finding: After an automated security review, condensing checks the artifact's directory below the project root before creating the new file and again just before the rename. A writer of the project directory could still swap the directory for a link between the second check and the rename. Closing it needs directory handles (`openat`/`renameat`, for example through `rustix`), a new dependency; the threat is a concurrent writer inside the user's own checkout. Done: on Unix, condensing opens every directory below the project root through the one above it without following a symbolic link (`rustix`, already in the lockfile through other crates) and writes and renames the file through that handle; a linked directory is refused even when it stays below the root. Windows keeps the two checks.

## Git branch as a shared folder (concept Question 38)

46. **Where the worktree lives.** `<store>/git/<branch with / as ->/`, below the store directory and outside the project's checkout, so the project's working tree never shows the branch. Alternative: a directory in `.git/`, rejected because Git owns it.
47. **Reset, not merge.** Before each sync the worktree is reset to the fetched branch; the own log is written again from the local store, so nothing is lost. A missing remote branch is created as an orphan branch.
48. **Named tracking ref.** Fetches go to `refs/remotes/<remote>/<branch>`, because `FETCH_HEAD` belongs to the worktree that fetched and a worktree cannot see the repository's.
49. **Commit and push.** Only `log/<own device>/` is staged; no change means no commit. Message `hone: log of <device>`. A rejected push is retried three times after a fetch and a rebase, which cannot conflict. Commits use the repository's Git identity.
50. **Names.** Remote and branch may hold only ASCII letters, digits, `/`, `.`, `_`, `-`, must not start with `-` and must not contain `..`, because both reach the Git command line as arguments.
51. **Errors.** A failing Git command ends the sync as `unavailable` with Git's message.
52. **MCP.** `hone mcp --sync-git <branch>` (or `HONE_SYNC_GIT`) uses the remote `origin`; there is no `--sync-remote` yet. (Since item 81, `--sync-remote` exists.)
53. **Not covered by tests yet:** the push retry after a rejected push.

## Contexts (concept Question 39)

54. **A local `contexts.yaml`, no secret.** In the platform's configuration directory (`HONE_CONFIG_DIR` replaces it). A context holds a peer (`server`, `folder`, or `git` with `remote`), an optional author, and `token_env`, the name of the variable that holds the token. Alternative: store the token, rejected because a file with tokens leaks them; an OS keyring is left for later (since item 89, a token can be stored in it).
55. **Precedence.** A flag or its environment variable wins; only without them does `hone sync` take the context's peer and a writing command the context's author. `--author` and `--role` now go together.
56. **The file is written anew.** `hone context set` and `use` rewrite it in the strict profile; comments are lost. Unknown keys, a peer with more than one kind, and a binding to an unknown context are rejected when reading.
57. **Names.** A context name is lowercase letters, digits, and `-`, not starting with `-`.
58. **The GUI leaves the author to the context** when its author or role field is empty, instead of passing empty flags.
59. **Not done:** the MCP server does not read contexts yet (it keeps `--author`, `--sync-*`); `export` and `forget`; tokens in an OS keyring. (The MCP server reads contexts since item 78; `export` and `forget` exist since item 82; tokens in an OS keyring since item 89; plugins for other languages are open, item 94.)

## `module-anchors-resolve` (concept Question 40)

60. **What is checked.** Every anchor and `interface.code` of the artifacts of the kind in `params.kind` (default `module`), against `/project`. `path`: the file or directory exists; `glob`: at least one file matches (`*`, `?`, `**` as in `change-needs-binding`); `symbol`: the file exists and, in a `.rs` file, the symbol resolves.
61. **Rust symbol resolution.** `a::b` resolves through items (fn, struct, enum, trait, type, const, static, union, inline `mod`, `macro_rules!`), enum variants, trait items, named struct fields, and items of `impl` blocks of a type named like the last path segment, also when the type is defined elsewhere. Re-exports (`pub use`) and out-of-line `mod x;` files are not followed. Alternative: rust-analyzer-level resolution, rejected as far beyond a WASM plugin.
62. **Codes.** Errors `anchor-missing`, `symbol-missing`, `unparsable`; warnings `symbol-unchecked` (symbol in a non-Rust file whose file exists) and `other-repository` (`repository:path`, not visible to the check). Each finding carries the artifact's path and the anchor's pointer (`/anchors/<i>`, `/interface/code`).
63. **Test cases.** One cause per case, as the gate test suite requires. The test projects' module kind has no extra schema, so `interface` shows the warning `unknown-field` of `schema-valid`; the expected lines include it.
64. **A binding holds the checkout's root.** An automated security review noted that a context was bound by the project ID from the repository's own `.hone/config.yaml`, so a foreign checkout could claim a bound project's ID and inherit its peer and author. A binding is now `{ context, root }` with the canonical root; in another checkout `hone sync` and the writing commands fail with a message to bind that checkout. Alternative: ask for confirmation, rejected because hone has no interactive prompts.

The plugin chapter states what the schema and the code do. Either the entry drops `hash` where there is no content hash, or the artifacts chapter names it a hash of the content that only `decided` artifacts bind approvals to; for the maintainer.

## Contexts in the MCP server (concept Question 42, confirmed by the maintainer on 2026-11-19)

78. **Same precedence, read once.** `hone mcp` takes the author and the peer of the tool `sync` from the bound context when its flags and their environment variables leave them out, each on its own: `--author` with a context peer is allowed, and the other way round. It reads the context once at the start, so the author and the peer stay fixed for the session as before, and an agent that edits `contexts.yaml` during the session changes nothing. Alternative: read the context per call, rejected because it would let the author change mid-session.
79. **A context it cannot use stops the start.** A malformed `contexts.yaml`, a binding made in another checkout, and a context server whose token variable is empty end `hone mcp` with exit code 1 and `hone mcp: <message>` on standard error, as a missing `HONE_TOKEN` with `--sync-server` already did. The context is read only when a flag is missing, so a fully configured server never reads it. Alternative: start without author or peer and fail per call, rejected because the reason would only show on the first writing call.
80. **An unreadable project has no context.** If the project's scope cannot be read (no `.hone/config.yaml`, no data directory), there is no project ID to bind, so the server starts without a context; its writing tools and `sync` then report the broken project themselves, and `resolve` stays usable to repair it.
81. **`--sync-remote`.** `hone mcp --sync-remote <name>` (default `origin`) names the remote of `--sync-git`, like `hone sync --remote`, because a context's Git peer carries a remote and the server now needs one. It has no environment variable, as `--remote` has none.

## `export` and `forget` (concept Question 43, confirmed by the maintainer on 2026-11-19)

82. **Export is a shared folder.** `hone export --to <dir>` copies the complete lines of every device's segments, byte for byte, below `<dir>/<workspace>/<project>/log/`, reusing the push of a folder sync. A sync with the directory as the folder imports it again, so no new format and no import command are needed. Invalid lines are copied as they are, because an archive keeps what was there. The device ID is not exported: an archive is not a device. Alternative: a single file (NDJSON or tar), rejected because it needs its own reader.
83. **Only into a new or empty directory.** A non-empty target is refused (`invalid`), and a project without a store is `unavailable`, both before anything is created, so an export never mixes with an existing state. The store is locked while copying.
84. **Forget asks for the project ID.** `hone forget --confirm <project>` must repeat the project ID of the root; anything else is `invalid` and removes nothing. hone has no interactive prompts (item 64), so the repetition is the confirmation. A project without a store is forgotten with zero events, so a repeated call succeeds.
85. **What forget removes.** The whole store directory (every device's log, the device ID, the lock file, the Git worktrees), an empty workspace directory above it, and the project's binding in `contexts.yaml`; the context stays, because other projects of the tenant may use it. It does not follow symbolic links. `contexts.yaml` is read before anything is removed. Copies in a shared folder or on a server stay; the result names the removed events per device and the unbound context.
86. **Git worktrees.** After removing worktrees of `hone sync --git`, hone runs `git worktree prune` in the project root and ignores its failure, because Git drops stale registrations itself. Not covered by tests yet.
87. **No MCP tools.** An export writes outside the project, which the MCP server avoids (its sync peer is fixed for the same reason), and forgetting is a decision of a person, as approvals are (item 42).
88. **Not done:** encrypting the local store per project, which the concept names as optional.

## Tokens in the OS keyring (concept Question 44, confirmed by the maintainer on 2026-11-19)

89. **The crate `keyring` 4.2.0, always built in.** Its `v1` mode picks Keychain Services, the Windows Credential Manager, or the Secret Service through `zbus` (pure Rust, no `libdbus`). It adds about 45 crates to `hone-cli` only; `hone-core` stays free of it, because credentials are tool. Like Extism, it has no feature switch.
90. **One entry per context and server.** Service `hone`, account `<context> <server>`. A token stored for a context is not found after the context's server changes, so it is never sent to another server. Alternative: the context name alone, rejected for that reason; the server alone, rejected because two contexts with different identities can share a server.
91. **The environment wins.** A context's token is the variable of `token_env` (default `HONE_TOKEN`) when it is set and not empty, otherwise the keyring's token, as a flag wins over the context (item 55). Without a keyring (`NoDefaultStore`, for example on a server without a desktop session) there is simply no stored token; any other keyring error is appended to the message `no token for the server: set <variable> or store one with hone context login <name>`. `--server` and `--sync-server` without a context still read only `HONE_TOKEN`, because there is no context to look up.
92. **Login reads standard input.** `hone context login <name>` reads one line from standard input, never a flag, because a flag shows in the process list and the shell history. It refuses an unknown context, a context without a server, and an empty line before it touches the keyring. `hone context logout <name>` reports whether a token was removed (`removed`). `contexts.yaml` gains no field: whether a token is stored is the keyring's state alone.
93. **Not covered by tests:** storing and reading a real keyring entry, because tests must not write into the developer's keyring; the precedence is unit-tested with a stand-in, the refusals end to end, and the round trip was smoke-tested against KWallet.

## Language plugins for other languages (direction chosen by the maintainer on 2026-11-19)

94. **Open: the contract of `resolve` and `public_api`.** `spec/plugins.md` names the entry points `resolve(anchor)` and `public_api(path)` of a language plugin, but neither `schemas/plugin.schema.json` nor the concept gives their input and output, how the host picks the language plugin for a file (by extension, by configuration), or which gate calls them. Today `module-anchors-resolve` and `public-api-has-decision` resolve Rust inside the gate itself. A plugin for another language could be built now only by copying such a gate per language, which would settle the design that the entry points are meant to answer, so it is not built in this run. For the maintainer: (a, recommended) a language plugin exports `resolve` and `public_api` with shapes in `plugin.schema.json`, the configuration maps file extensions to language plugins, and the two gates call the mapped plugin for files that are not theirs; (b) one gate per language with the codes of `module-anchors-resolve`, and the entry points are dropped from the specification; (c) the gates stay Rust-only until a team asks for another language. The maintainer chose (a); the contract is designed as a step of its own before any plugin for another language is built.

## The commands of a ticket (concept Question 45, build-time rules)

The decisions of Question 45 were taken with the maintainer; these rules came up while building and are reported for confirmation.

95. **The record's shape.** `id`, `type`, `project`, `profile`, `config` in this order, then `attributes` as one flow map and `external` as a list of flow maps, every string double-quoted, so the record stays in the strict YAML profile whatever a value holds. The record is checked like any artifact (`schema-valid` rules) before it is written.
96. **Rewriting a record.** `set-attributes` and `switch-config` remove the top-level key and the lines that continue it, and append the new `key: value` at the end, so every other byte (comments too) stays. An empty attribute set removes `attributes`. A record with carriage returns is refused.
97. **Order and rollback.** Every command checks everything first, then writes the snapshot (if new), the record, and the event; if the event cannot be written, the record (and a snapshot it created) is removed or gets its old bytes back. Files below the project root are created through directory handles that follow no symbolic link (`below.rs`, as condensing does since item 45).
98. **A switch without change is refused**: `the ticket <tk> already uses the current configuration`, so the log gets no empty `ticket.config_changed`.
99. **Values and IDs.** `--attribute` integers are 64-bit; `--external` splits at the first `:` and the first `=`, so a URL may contain both. A new ticket ID is rolled again while its record path exists (item 73). The MCP tool `ticket_start` takes the attributes as typed JSON and uses the server's packages directory.

## Language plugins (concept Question 46, build-time rules)

The decisions of Question 46 were taken with the maintainer, including one package per language instead of `hone/standard`, after it turned out that a plugin in a package must be approved before any project extending the package resolves. These rules came up while building.

140. **`lang-rust` replaces both Rust plugins.** The symbol resolution of `module-anchors-resolve` and the public API of `public-api-has-decision` moved unchanged into the language plugin `lang-rust`; the two gate plugins are gone. It parses each file once per call. It returns no `line`, because `syn` gives line numbers only with an extra feature of `proc-macro2`; `line` is OPTIONAL.
141. **The host checks paths and globs.** An anchor path must be relative, without `..`, and below the project root after following symbolic links, otherwise it does not exist. A glob walks only below its literal prefix and follows no symbolic link to a directory. The rule for another repository is the plugin's: a `:` before `#` (not `::`).
142. **`public-api-has-decision` keeps its behaviour.** One finding per changed file, at the changed file's path; a base that does not parse counts as an empty API; a file missing in a state is not passed to the plugin and has an empty API. Changed paths of another repository are skipped.
143. **A language plugin named as a gate** is a `reference` error at the gate entry (`` `lang-a` is a language plugin, not a gate ``). New test cases: `resolve/language-plugin`, `resolve/error-language-conflict`, `resolve/error-language-gate`, and `check/plugin-public-api-unchecked`; the 17 gate cases of the two former plugins now use `lang-rust`, regenerated by a throwaway script outside the repository, keeping the deliberate defects of the plugin-hash cases.
144. **The package `hone/lang-rust` lives in `schemas/lang-rust/`**, next to `schemas/standard/`, with the plugin file and the module; a test checks that its module has the bytes of the test cases. Copying the module into `.hone/plugins/` stays the tool's job (no command does it yet).
145. **Not covered by tests yet:** `plugin-failed` for a language plugin that returns a list of another length, and one failing language plugin next to a working one, because no test plugin exports `resolve` or `public_api` yet.

## GUI (maintainer request)

Tool decisions taken for the maintainer's request to rebrand the GUI, replace free text by selection, add a ticket tracker, and show a ticket's progress. None changes `schemas/`, `spec/`, or `.hone/config.yaml`.

100. **`hone artifacts` and `hone ticket show` are new** (supersedes the open part of item 29). The GUI needed the ticket records, the artifacts for an anchor, a ticket's profile steps, and the roles of its snapshot, and no command printed them. `hone artifacts [--json]` lists every artifact of the checked directory, ticket records included, with `id`, `type` (from the path), `path`, `ticket`, `title`, declared `status`, `effective` status, and for a ticket record `profile` and `external`, plus `project` and `unreadable`. `hone ticket show --ticket <tk> [--json]` prints the record's `profile`, `config`, `attributes`, `external`, the snapshot's `roles`, and the profile's `steps` with `requirement`, `title`, and `after`. Both live in `hone-core` (`catalog`, `ticket_overview`) and exit with 1 and `{ status: "error", message }`. Alternatives: one `hone project` command with everything, rejected because it mixes a directory listing with a ticket's snapshot; reading `.hone/resolved.json` in the GUI, rejected because the command line is the GUI's only interface.
101. **The order of a profile's steps.** `steps` of `hone ticket show` follows spec/gates.md item 4: a step comes after the steps it `requires` and after the steps whose `outputs` meet its `inputs` (`ticket` is no step); steps that no order separates keep the order of their names, and a cycle of inputs and outputs puts its steps at the end in the order of their names. Alternative: the order of the configuration file, rejected because the resolved configuration is canonical JSON and keeps no order.
102. **Titles of artifacts.** The catalog's `title` is the field `title`, otherwise the first `# ` heading of a Markdown body. The protocol has no title field; this is display only.
103. **Done on 2026-11-19 at the maintainer's request: the tools `catalog` and `ticket_overview`.** The original note: **The MCP server offers neither command yet**, as with `hone log` (item 27). Concept Section 12 says the server offers one tool per public function of `hone-core`; `catalog` and `ticket_overview` are read-only and could become tools `catalog` and `ticket_overview`. For the maintainer: add them, or record that GUI listings are exempt.
104. **Accent and shades.** The orange accent is gone. Accent `#6b8cff` (dark) and `#1d4ed8` (light), from the logos; hover `#8ea8ff` and `#1e40af` (lighter in dark, darker in light, so the hover always moves away from `bg`); a muted fill `#1a2033` and `#ebeffb` (16 % and 9 % of the accent over `bg`) for the highlighted choice of a list. Text on the accent is `#0b0b0c` in dark (6.4:1) and `#ffffff` in light (6.7:1). Accent text on `bg`, `surface`, and the muted fill passes 4.5:1 in both themes (lowest 5.3:1). The focus ring stays the accent.
105. **Logo and wordmark.** The top bar shows the logo in the variant of the theme (both SVGs inlined, CSS hides the other one, so the manual theme switch works too) and the wordmark `hone` without the cursor. The window icon is the dark variant rendered at 256 px into `gui/assets/icon.png` and decoded with the crate `png`, because the web view's window takes RGBA pixels, not SVG. The dark variant's blue is mid-tone and reads on light and dark task bars.
106. **`dark:` follows the theme switch.** rust-ui's `dark:` classes followed only the system preference, so the light theme on a dark system kept dark inputs. A custom Tailwind variant now applies them for `data-theme="dark"`, or for the system preference unless `data-theme="light"`.
107. **A combobox of hone's own.** rust-ui's Select needs an inline script (item 24), so `src/ui/combobox.rs` is new: a text field that filters a list by value, label, and note, with arrow keys, Enter, Escape, the ARIA combobox pattern, and optionally "Use “…”" for a new value. Lists: tickets (records, then tickets known only to the store), steps (the cells of the step track are the selection), thread kinds (`question`, `concern`, `suggestion`, `note` from hone/standard plus the log's kinds, or new), artifacts for an anchor (the ticket's first), the event log's filters (exact type and ticket instead of substrings), the check's ticket, the author, and the role.
108. **Author and role.** Author choices are the context's author (`hone context show`) and every author of the log, with the roles they wrote with; a new handle can be typed. Role choices are the roles of the open ticket's snapshot (`hone ticket show`), because a write is checked against that snapshot; without an open ticket the list is empty and free entry stays possible. Choosing a known author with an empty role fills the role they last wrote with, if the ticket has it. Both empty still means the context's author (item 31).
109. **Progress: states and the current step.** A step is done, skipped (with its reason), open, or waiting: open while a step in its `after` is neither done nor skipped. Waiting is information, not a lock: spec/gates.md item 4 says no gate checks readiness, so the GUI lets the user finish a waiting step. The current step is the first open step that waits for nothing. The ticket list shows the same states as a segmented bar per ticket, which costs two command calls per ticket row.
110. **Progress: gates per step, pure only, automatically.** The ticket screen runs `hone check --ticket <tk> --class pure` when it opens and after every write and assigns gates to steps by the `<step>/` prefix of their name. `exec` gates are left out, so that opening a ticket never runs a project's command; the full check (with `exec`) stays a button on the Checks screen. Optional steps show no gates, because `hone check` runs only the gates of required steps. Alternative: run the full check automatically, rejected for the reason above; run nothing automatically, rejected because the request asks for gates passed or failed at a glance.
111. **`changed-paths-missing` is not a failure in the GUI.** A `change-needs-binding` gate without changed paths fails with `changed-paths-missing`; the GUI has no change to pass, so such a gate is shown as "needs changed paths" with a hint to the hook or CI, not as failing. The Checks screen still shows the raw result.
112. **Where the tracker setting lives: `gui.json` next to `contexts.yaml`.** It is a file of the GUI in hone's configuration directory (`HONE_CONFIG_DIR` or the platform's), keyed by project ID and canonical root like a context binding, so a repository cannot claim another checkout's tracker and another checkout asks again. JSON, because the GUI has no YAML parser and the file is written only by the GUI. Alternatives: a field in `contexts.yaml`, rejected because that file belongs to the command line, has a strict schema, and binds a project to one context while a tracker belongs to the project; a field in `.hone/config.yaml`, excluded by the request; the OS keyring, rejected because the setting is no secret. The README's earlier "it stores nothing itself" no longer holds for this one file.
113. **GitHub: suggested from `origin`, read through the search API.** `git remote get-url origin` in the root is parsed for `github.com` URLs (https, ssh, scp form) and SSH host aliases that contain `github` and no dot (`git@github-work:o/r.git`); GitHub Enterprise is not suggested. Listing and searching use `/search/issues` with `repo:<o>/<r> is:issue` (plus `is:open` without words, sorted by update), because the issue list of a repository mixes in pull requests; `#12` fetches the issue directly. 50 results, no paging.
114. **Jira: Cloud with an account email, Server without.** With an email, the token is an API token sent as Basic auth to `/rest/api/3/search/jql` (the Cloud endpoint since 2025); without one, a personal access token sent as Bearer to `/rest/api/2/search`. JQL: `project = "<KEY>"`, without words `AND statusCategory != Done`, with words `text ~ "<words>*"`, and a key like `PAY-12` also matches `key`. Ordered by update, 50 results.
115. **Tokens: environment first, then the keyring.** The variable is the setting's `token_env`, default `GITHUB_TOKEN` or `JIRA_API_TOKEN`; when it is set and not empty it wins, otherwise the keyring entry service `hone`, account `tracker <API address>` (`https://api.github.com` or the Jira base URL), the same precedence as contexts (item 91). The screen stores and removes the keyring entry; the token is never written to a file. The crate `keyring` 4.2.0 joins the GUI workspace.
116. **What picking a tracker ticket does.** A ticket record links a tracker ticket through `external` (`system: github` with the issue number as `key`, or `system: jira` with the issue key); the GUI matches `system` without case and a GitHub key with or without `#`. Picking a linked tracker ticket opens the hone ticket; an unlinked one offers to copy its `external` entry for a ticket record. The GUI writes no ticket record and starts no ticket, because starting a ticket (ID, profile selection, frozen configuration) is Section 16, step 10, and has no command yet. A linked ticket's page takes its title from the tracker.
117. **Opening addresses in the browser.** External links open with `xdg-open`, `open`, or the Windows URL handler, and only for `http` and `https`, so a value from a tracker or a ticket record cannot start a program.
118. **More from the mockups.** An Artifacts screen (tabs by kind with counts, effective-status filter, search, `superseded` struck through, unreadable files in a `bad` panel); navigation counts (tickets, artifacts, open threads, failed gates of the last full check); the ticket head with attribute tags (`risk: high` framed in `bad`), the profile inverted, the configuration hash muted, external links; the ticket's artifacts beside its threads; threads listed by their first line, anchor, and author, messages with author, role, and time; the check run with an exit note and duration, kept across screens; the event log with time, device, and the event's keys muted and its type in the accent. Times come from the UUIDv7 of the event ID and are shown in UTC. Not built: the link graph, profiles, and plugins screens (no command yet), a global search in the top bar, and the "Request changes" action of a thread (it is an approval of an artifact, `hone approve --changes-requested`, which the GUI does not call yet).
119. **Not covered by tests:** the views themselves (Dioxus components are checked by running the app, see the screenshots of this run), the requests against the real GitHub and Jira (GitHub was smoke-tested against a public repository, Jira against a local stand-in server), and the keyring round trip of the tracker token, because tests must not write into the developer's keyring. Request building, answer parsing, remote parsing, the settings file, matching, progress, and filters are unit-tested; the command line calls are tested against the real binary.
120. **Errors are red.** Could-not-run and refusal boxes, tracker errors, failed gates, refused writes, and invalid fields use `bad` (border, title, glyph `✕`), never the accent. This overrides the design system's "Alert with accent frame" for exit 2, at the maintainer's request. An invalid field carries `aria-invalid`, and one CSS rule keeps its border and focus ring `bad`. A refusal (`invalid`, `refused`) is titled "hone refused it", any other failure "hone could not run". The writer fields are invalid when only one of author and role is set (a write would then fall back to the context's author) or the role is not in the open ticket's configuration; tracker form fields are invalid when the setting names them as wrong.
121. **`hone artifacts` carries the ID links** (`links`, by type) so that the graph and the artifact page need no further command. The `ticket` edge comes from the existing `ticket` field. Only the ID links of concept Section 5 are listed; `links.code` is no artifact link. This changes the JSON of `hone artifacts`, which the MCP tool `catalog` being added in the main checkout returns too.
122. **`hone review show` is new.** The GUI must show who approved the current content without reimplementing the rule of condensing, so `hone-core` exposes it: `ProcessStore::review` returns the current hash, the last decision per person and role (the same function condensing uses), the confirmations, and the file's `review` block. It writes nothing and needs no store. Alternative: compute the decisions from `hone events` in the GUI, rejected because the GUI never reimplements a protocol rule (item 28).
123. **Link graph layout.** One column per kind, ticket records first, then by link balance (received minus stored, ascending, so arrows point right), each column ordered by two sweeps of the barycentre heuristic, links within a column bend to the left, links across a column run through the gap between rows. Ticket records and `ticket` links start hidden, because one dashed line per artifact hides everything else; the ticket filter replaces them. Labels show on hover or focus, or always with at most twelve links. No zoom; the graph scrolls inside its frame. Alternative: a force layout, rejected because it moves on every change and is not deterministic.
124. **Opening a node.** Click or Enter opens an artifact on the Artifacts screen or a ticket on the Tickets screen; hover or focus highlights its links. The artifact page has no rendered body, because no command prints it; "Open the file" opens it with the system's program, only for a regular file under the project root after canonicalizing.
125. **Review actions.** Approve and Request changes call `hone approve [--changes-requested] [--proof …]` as the chosen author; the command line checks the role and `actors`, and a refusal shows in `bad`. Condense calls `hone review condense` without a summary (the AI drafts summaries, concept Question 37), enabled once somebody approved the current content. Confirm calls `hone review confirm`, enabled when the file has a `review` block. Opening an artifact with a ticket makes that ticket the open ticket, so the role list matches the snapshot the approval is checked against.
126. **Global search.** Ctrl+K or Cmd+K anywhere opens it (a page-level key listener reports to the app); arrows move, Enter opens, Escape or a click outside closes. Every word of the query must occur, ignoring case; at most eight hits per group in the order tickets, artifacts, threads, tracker. Tracker hits come from the tracker's search 350 ms after the typing pauses, need two characters, and a tracker ticket that a record names opens the hone ticket. Threads match by their opening message's first line.
127. **Profiles and plugins screens are left out.** The profiles matrix needs every profile, step, and the layer each comes from; plugins need the plugin definitions, capabilities, and the lockfile's approvals. No command prints the resolved configuration or the lockfile, and `hone ticket show` gives one ticket's profile only; a matrix assembled from tickets would miss unused profiles and mix snapshots. Both wait for a command that prints the resolved configuration (for example `hone resolve --show --json`), which is a decision for the maintainer.
128. **Not covered by tests:** the views (checked by running the app; screenshots of this run), the page-level key listener, and the real tracker in the search (smoke-tested against a public GitHub repository). The graph layout, links both ways, search matching, tracker hits, review commands through the real binary, and the failure titles are tested.
