# hone-gui

The desktop GUI of hone for Linux and Windows (concept Section 12, "Desktop GUI"). It is built with Dioxus on the system web view and talks to hone only through the command line: every screen calls `hone … --json` as a child process. It never links `hone-core`, so the JSON of the command line is its interface. The one exception is the ticket tracker, which is tool behaviour of the GUI alone (see below).

It is a Cargo workspace of its own, because the web view needs system libraries that the protocol crates do not: on Linux WebKitGTK 4.1 (`webkit2gtk-4.1`, `libsoup-3.0`), on Windows the WebView2 runtime.

## Run

```sh
cargo build -p hone-cli                     # at the repository root: the hone binary
cd gui && HONE_BIN=../target/debug/hone cargo run -- <project root>
```

`hone` is found through `HONE_BIN`, otherwise next to `hone-gui`, otherwise on the `PATH`. The GUI passes its environment on, so `HONE_DATA_DIR`, `HONE_CONFIG_DIR`, `HONE_TOKEN`, `HONE_SYNC_FOLDER`, `HONE_SYNC_SERVER`, `HONE_AUTHOR`, and `HONE_ROLE` work as on the command line.

## Layout

The window follows the mockups of GUI v2 (concept Section 12, "Desktop GUI"): a **header** with the project switcher (which also opens the project settings), the views outside a ticket, the open ticket as a chip, the search, and the author and role; the **centre**; and a **status bar** with the open ticket's profile, snapshot hash, current step, failing pure gates, threads, the last sync of this window, the own device, and the theme. Opening a ticket shows its **workspace**: the explorer on the left (collapsible to a rail), the ticket's tabs in the middle, and the assistant on the right. Every ticket keeps its tabs until the window closes; the Overview is always open.

The **Tickets** view lists `hone ticket list` in the tabs Mine (started by the author or with an event of theirs), Open (not complete), Needs me (a reason in `waiting` names the author's role), Completed, and Tracker. A row shows the steps as squares (filled done, dashed skipped, accent the current step), the first reason the ticket waits (`your approval` when the role is the author's), and how long ago its newest event was written; a click shows the preview, a double click or Open ticket opens the workspace.

The **Overview** shows the head (attributes, profile, external tickets, who started the ticket and when), the **Next** card, the steps, and the newest four entries of the Journal. The Next card names the current step and the first error finding of a gate of that step in the window's pure check; for `public-api/changed-without-decision` it offers Draft decision. Without such a finding it shows the first reason of `waiting`. A click on a step opens the panel that sets it (`hone step set`). The GUI runs `hone check --ticket <tk> --class pure --source gui` when a ticket opens and after every write, so no `exec` gate runs a command behind the user's back, and the run is stored. A gate whose only error is `changed-paths-missing` is shown as needing changed paths, not as failed, in the explorer, the step panel, and the status bar, because the GUI knows no change. The **Journal** tells the ticket's events and stored runs in sentences, newest first.

The **Check run** tab shows a stored run of `hone runs`: the time, source, and device, the command line its arguments give, the exit code, the passed and failed gates, the time, and every gate (failed first) with its class, time, and findings. A finding's file opens as an artifact or code tab. **Run again** repeats the run's step, changed paths, and class with `--source gui` and shows the new run in the same tab; `--base` and `--lock` are left out, because they name paths of the caller that may be gone. Open finding on the Overview and Check run in the explorer open the newest run; without one, the tab runs every gate on demand. Ask assistant waits for the assistant.

The **Event log** tab shows the ticket's events of `hone log`, newest first: the time (the clock for today, otherwise the date, UTC), the device and `seq`, the type, and a summary of the payload. The type filter offers every type and, for two types or more with the same prefix, the family (`thread.*`). The selected event shows below in full, with Copy JSON. The Sync view shows the whole store the same way, with a filter by ticket.

The link graph places artifacts in one column per kind, ordered so that the kinds that store more links than they receive stand left, and orders each column by the rows of each node's neighbours. A link across a column runs through the gap between two rows, so it never passes behind a node. A node shows its kind, ID, title, and effective status (the declared one without). Hovering or focusing a node shows its links and their types; a click selects it for the **inspector** (declared and effective status, the links it stores and the computed links it receives, Open, and Center here), a double click or Enter opens it. Ticket records and their links start hidden. In a ticket the tab shows **this ticket** (its record, its artifacts, and their direct neighbours) or the **whole project**, and **focus mode** collapses the explorer and the assistant until it is left, restoring them as they were. The Artifacts view shows the same graph for the whole project under **Graph**, beside **List**.

An artifact's review shows its stored links and the links other artifacts store towards it (marked computed), the threads anchored to it, and its approvals in its ticket: every person's last decision, whether it is for the current content, the condensed `review` block, and the actions Approve, Request changes (with an optional proof), Condense into the file, and Confirm the review block. They write as the chosen author. Inside a ticket an artifact opens as a tab; outside, on the Artifacts view, where opening it makes its ticket the open ticket.

The search (Ctrl+K or Cmd+K, or the field in the header) finds tickets by ID and external key, artifacts by ID, kind, and title, threads by their first line, and, with a tracker, the tracker's tickets (after a pause in typing). Every word must match. A tracker ticket that a ticket record names opens the hone ticket; any other one opens the Tracker tab on it.

**Profiles** shows every step against every profile (`required`, `optional`, or `–`) and the selection rules; **Plugins** shows every plugin of the configuration with its extensions, the capabilities it asks for beside the approved ones, and its hash, then the plugins the lockfile approves that the configuration does not use and the approved commands. Each definition names the layers it comes from, bottom to top. Both read `hone resolve --show` with the packages directory of the settings, so they show the sources, not `.hone/resolved.json`; while that file is out of date, they say so and offer **Run hone resolve**. A failed resolution shows its problems, and the Plugins screen then the lockfile's approvals.

**New ticket** (Tickets view, or Start ticket on an unlinked tracker ticket in the Tracker tab or the search) runs `hone ticket start`. Attributes are rows of name, type (text, number, yes/no), and value; a text is passed double-quoted, so `3` typed as text stays text. Names that the selection rules test are offered with their values. While typing, `hone ticket select` shows the profile and the rule that matched; another profile can be chosen, with a warning that `steps-complete` will report `profile-not-selected`. On success the new ticket opens. On the Overview, **Edit attributes** runs `hone ticket set-attributes` with only what changed and the names removed, and **Switch to current rules** runs `hone ticket switch-config`; both say whether `select` still gives the ticket's profile. The head shows `profile-not-selected` while `selected` of `hone ticket show` differs from the profile. A refusal for a stale `.hone/resolved.json` offers **Run hone resolve**.

**Editing an artifact.** An artifact opens as a tab in a ticket, or on the Artifacts view outside one, in four modes. **Fields** shows the front matter as fields and, for a Markdown file, the body in a source editor. `id`, `type`, `ticket`, and `review` are not fields, because the path fixes the first three and `hone review condense` writes the last. A field is shaped by its value or, while absent, by the kind's schema: text, number, yes/no, a list of strings one per line, a map of strings, or, for anything else, its JSON with a pointer to Source. `status` is a list of the kind's statuses, `links` lists each ID link type with a searchable list of artifacts plus the `code` references, and `anchors` are rows of kind and reference. A changed field is written anew in the strict YAML profile (strings double-quoted, lists of scalars in flow style); every other field keeps its bytes, comments included (`src/artifact_text.rs`). **Source** shows the whole file, **Split** the source beside its preview, and **Preview** the review inline (`src/features/review.rs`): the rendered artifact with the passages its threads quote marked and numbered (the first place the quote occurs in one piece of text), its anchors and code and its links both ways below, and beside it the threads anchored to it in the order of the log, with a note when the quote is not found or the thread's hash is not the current content. One thread is open with its conversation and a reply: the one chosen last, otherwise the first open one; resolved threads show on request. **Open thread** quotes the text selected in the window and writes in the open ticket, otherwise in the artifact's ticket; **Resolve thread** or **Reopen thread** acts on the open thread. The approvals and their actions stand below the threads. A thread anchored to an artifact, opened from the explorer or the search, opens that artifact's review. An artifact whose saved status is binding is read-only: it opens in Preview, has no Fields mode, Save, Discard, or Propose, and its source editor does not accept input; **Supersede** asks for a title and runs `hone artifact new --supersedes <id>` with its kind in the open ticket, then opens the new artifact. The GUI parses no YAML: after an edit of the source, the fields wait until the file is saved or the change discarded. 400 ms after the text last changed, `hone artifact check` checks it unsaved; the Problems list shows each finding with the line of the key its pointer names (`src/artifact_text.rs`), and a click shows that line in the source. Error findings are red and mark the field they point into, warnings are amber. Unsaved text stays in the window while another tab is shown; the tab shows a dot, and closing it asks to save, discard, or cancel. Save sends the text to `hone artifact save`, which writes it only without an error finding. An artifact in `draft` whose kind has `proposed` offers **Propose**, which saves it with that status. The preview renders Markdown with `pulldown-cmark`, shows raw HTML as text, and turns links and images into text, so a body can neither run a script nor load anything. **New artifact** (Artifacts screen) runs `hone artifact new` with a kind, a title, the ticket for a decided kind, and anchors, as the chosen author, and opens the new artifact.

**Code.** An anchor or a code reference (`path`, `path#symbol`) opens the file read-only at the line the language plugin gives for the symbol (`hone file show --symbol`): inside a ticket as a tab of its own, on the Artifacts view in a panel at the right edge; a missing symbol, a file without a plugin, and an unparsable file open at line 1 with an amber note. A glob and a reference into another repository open nothing. **Open in IDE** starts the project's IDE at that line; Ctrl+click (Cmd+click) on an anchor does so directly. The IDE is a setting per project and checkout: VS Code (`code --goto {file}:{line}`), Zed (`zed {file}:{line}`), a JetBrains launcher (`<launcher> --line {line} {file}`), or a custom program with one argument per line. It runs without a shell, and only for a regular file below the project root after canonicalizing.

The editor is CodeMirror 6, bundled into `assets/editor.js` with esbuild from `editor/editor.js` (`npm run gui:editor`, the packages pinned in `package.json`) and committed like `assets/hone.css`, so the window loads nothing from the network.

Errors, failed gates, refused writes, and invalid fields use `bad`, never the accent; warnings (a finding of level `warning`, `profile-not-selected`, an unresolved symbol) use `warn`, amber (`#b45309` light, `#fbbf24` dark, both above 4.5:1 on `bg` and `surface`); an invalid field keeps a `bad` border and focus ring.

Wherever the set of values is known, a field is a searchable list (`src/ui/combobox.rs`): tickets, steps, thread kinds (hone/standard's four plus the kinds in the log, or a new one), artifacts for an anchor, the event log's filters, the author (the context's author and the authors of the log, or a new handle) and the role (the roles of the open ticket's configuration). Arrow keys move, Enter selects, Escape closes.

The source has one module per feature under `src/features/`, the command line client in `src/hone.rs`, the tracker in `src/tracker.rs`, and the components in `src/ui/`.

## Tracker

The Tracker tab of the Tickets view keeps, per project and checkout, where the project's tickets live: a GitHub repository (suggested from the Git remote `origin`) or a Jira project (base URL, project key, and the account email for Jira Cloud). It lists the open tickets or searches them, opens the hone ticket whose record names one in `external`, and copies the `external` entry for a ticket that no record names yet. A ticket whose record names a tracker ticket takes its title from the tracker.

The setting lives in `gui.json` in the hone configuration directory (`HONE_CONFIG_DIR`, otherwise `$XDG_CONFIG_HOME/hone/`, `%APPDATA%\hone\`, or `~/Library/Application Support/hone/`), next to `contexts.yaml`, keyed by project ID and the canonical root like a context binding:

```json
{
  "projects": [
    {
      "project": "prj-8m2k4d7q",
      "root": "/home/alice/acme/payments",
      "tracker": { "kind": "github", "owner": "acme", "repo": "payments" },
      "ide": { "kind": "jetbrains", "launcher": "rustrover" },
      "packages": "/home/alice/hone-packages"
    }
  ]
}
```

The project settings (from the project switcher) set `ide` (`{ "kind": "vscode" }`, `{ "kind": "zed" }`, `{ "kind": "jetbrains", "launcher": "…" }`, or `{ "kind": "custom", "argv": ["nvim", "+{line}", "{file}"] }`) and `packages`, the directory passed as `--packages` to `hone resolve`, `hone ticket start`, and `hone ticket switch-config`. An entry without settings is removed.

A Jira entry is `{ "kind": "jira", "base_url": "https://acme.atlassian.net", "project_key": "PAY", "email": "alice@acme.example" }`. Either may name `token_env`. The token never goes into a file: it comes from that variable (default `GITHUB_TOKEN` or `JIRA_API_TOKEN`) when set and not empty, otherwise from the OS keyring under the service `hone` and the account `tracker <API address>`, where the screen stores and removes it. GitHub works without a token for public repositories, at a low rate limit.

## Checks

After a change under `gui/`, in this directory:

```sh
npm run gui:css          # at the repository root, after a change to classes or to assets/input.css
npm run gui:editor       # at the repository root, after a change to editor/editor.js
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test               # needs the hone binary: cargo build -p hone-cli at the repository root
```

`tests/cli.rs` runs the real command line against a copy of a gate test case, so a change to the JSON of the command line turns it red. The tracker's requests and answers are unit-tested without a network; no test talks to GitHub, Jira, or the OS keyring.

## Components

The components in `src/ui/` come from [rust-ui](https://rust-ui.com/docs/components), the Dioxus registry, under the MIT License (Copyright (c) 2026 Max Wells). They keep rust-ui's Tailwind v4 classes; `assets/input.css` maps rust-ui's theme names onto hone's design tokens, removes every radius and shadow, draws the focus ring as an outline, and makes `dark:` follow the theme switch. Taken: Alert, Badge, Button, Card, Checkbox, Input, Progress, Separator, Skeleton, Table, Tabs, Textarea. Changes: variants the GUI does not use are left out, the icon crate is replaced by inline SVG, router links and pointer handlers are left out, `Input` and `Textarea` report their value through `oninput`, and the malformed second selector of `TableCell` is fixed. Select is not taken, because it depends on an inline script; `Combobox` is hone's own.

The accent is indigo: `#6b8cff` in the dark theme and `#1d4ed8` in the light theme, with a hover shade (`#8ea8ff`, `#1e40af`) and a muted fill for the highlighted choice (`#1a2033`, `#ebeffb`). Accent text passes 4.5:1 on `bg`, `surface`, and the muted fill in both themes. The logo (`assets/logo-dark.svg`, `assets/logo-light.svg`) stands in the top bar in the variant of the theme; the window icon is `assets/icon.png`, the dark variant rendered at 256 px.

`assets/hone.css` is generated from `assets/input.css` with the Tailwind CLI pinned in `package.json` and committed, so that `cargo build` needs no Node.js. The fonts Inter and JetBrains Mono are used when installed and fall back to the system fonts.
